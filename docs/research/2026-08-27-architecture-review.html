01

Executive summary

Six findings that change the plan

First, the thing you need to know before reading anything else. github.com/zoworkhq/datagrid does not exist. I checked it directly, then checked five plausible variants and listed every repository in the zoworkhq organisation. There is no code, no README, no demo, no API and nothing to migrate. §02 sets out what actually exists. That changes this review from an audit into a design review — and, on balance, it is good news, because five of the twelve problems found below are the kind that cannot be fixed after the first release.

The previous brief was a good healthcare product document and a weak library-architecture document. It assumed React, assumed a single package, assumed a row model that FHIR cannot supply, claimed a performance tier that is not physically available, and left three security defects unaddressed. This review keeps the clinical thesis — which is still the reason to build this — and replaces the engineering underneath it.

The six findings that change the plan

  1. The core must be framework-agnostic, and the renderer must sit below the adapters. Not because framework agnosticism is fashionable — it is expensive, and §26 costs it honestly — but because the accessibility model and the virtualiser are the parts nobody should write twice. AG Grid and TanStack both prove the shape; the variation that makes it affordable is putting a framework-free DOM renderer between the engine and the adapters, so an adapter is 4 KB of binding with no grid logic in it.
  2. The engine should be signal-based. TanStack Table v9 shipped on 4 August 2026 on the alien-signals architecture and measured +79% row processing, +52% grouping, and up to 86% less retained heap. TC39 Signals is at Stage 1 with Angular, Vue, Solid, Preact, Ember and MobX contributors behind it. A bespoke observer layer written in 2026 would be legacy by 2029.
  3. Client-side one million rows was never available. The same TanStack release reports 380 MB retained for one million rows by eight columns — the best number in the category, down from 2.71 GB. A clinical grid has forty columns and runs on a shared workstation with 4 GB and an EHR already open. The brief's performance table had a 1M+ client row in it. It should be deleted and replaced with a refusal.
  4. FHIR breaks the coverage sentence. Servers return opaque link.next URLs and the specification is explicit that a client must not construct its own. Bundle.total is optional; major servers omit or estimate it. So “Showing 8 of 1,284” — the sentence the entire coverage argument was built on — cannot be said against a large share of real FHIR servers, and neither can a page number. §06 shows what it has to degrade to.
  5. Three security defects, one of which is remote code execution. A patient's preferred name is free text they supply. Exported to CSV it is a formula, and Excel, Sheets and LibreOffice all execute it — OWASP's own note is that quoting fails once Excel re-saves the file. Separately: nothing prevented telemetry from carrying PHI, and nothing prevented a custom cell renderer from injecting raw HTML. None of these is a feature request. They are defects in the design as written.
  6. Our assumed AI differentiator has already gone. Syncfusion ships semantic filtering and anomaly detection in its grid today; MUI X v9 ships an AI assistant in Premium. The differentiator is not the AI features. It is provenance and refusal — being the only grid where an AI-derived value cannot be mistaken for a verified one, and where an uncompilable query runs nothing rather than approximating.

The recommendation, in one paragraph

Yes to a separate repository — and no to it being a separate product. Create zoworkhq/datagrid as a pnpm workspace of small packages, framework-agnostic from the first commit, depending on OxygenUI's L0 packages and nothing above them. Ship React only in wave one and do not claim agnosticism in public until the Angular adapter exists, because until a second adapter exists the claim is untested. Keep the clinical thesis intact. Fix the three security defects before the first export ships. Delete the 1M client-side row. And write the limitations copy before writing the disclosure code, because the one risk here that can damage the company rather than the product is being mistaken for a compliance boundary.

Current architecture assessment

Twelve judgements on the previous brief

Twelve judgements on the previous brief. Four survive unchanged, four need amendment, and four should be replaced. The pattern is consistent and worth naming: the clinical reasoning was strong and the library engineering was thin — which is what you would expect from a document written to answer a product question rather than an architecture one.

Top-competitor analysis

Six systems, architecture first

Six systems, not five. I added Glide Data Grid because it is the most architecturally interesting of all of them and because it settles a question that would otherwise keep being reopened: whether to render on canvas.

Everything dated or numbered below was checked in August 2026 against documentation, release notes, repositories or installed source. Where a claim could be measured rather than described, it was — the Ant Design rows in the previous brief came from reading antd@6.6.0 and @rc-component/table@1.11.1 in node_modules, and the same discipline applies here.

AG Grid36.1.0 · 5 Aug 2026Community MIT · Enterprise US$999/dev perpetual (1 yr updates) · bundle with AG Charts US$1,598

The category's reference implementation. Ten years of work in the virtualiser and the only genuinely mature server-side row model.

CoreFramework-agnostic TypeScript core with an IoC container, auto-wired services and its own internal component/data-binding framework. The framework packages are thin wrappers.
RenderingDOM virtualisation on both axes with a configurable rowBuffer (default 10 rows above and below the viewport) and node recycling — rendered nodes are cached and reused rather than unmounted.
StateState lives inside the grid, reached through a large imperative GridApi object.
Modulesv33 refactored module registration for tree-shaking: register only the feature modules you use. From v33 all community features export directly from ag-grid-community.
DataFour row models — Client-Side (everything in memory), Infinite (flat, block-loaded), Server-Side (Enterprise; lazy groups + server aggregation), Viewport (Enterprise; server knows your exact first and last row).
Themingv33 introduced a JS Theming API; legacy CSS themes now need { theme: "legacy" } — a breaking change for every existing consumer.
What to take
  • The four-row-model framing. It is the clearest mental model in the category and it names the trade-off honestly. Our brief collapsed all four into a single mode prop, which is a worse API.
  • The v33 module registry. Explicit feature registration with real tree-shaking is exactly the plugin shape we want.
  • Node recycling. Windowing alone is not enough; the cost is reconciliation of rows entering and leaving.
  • The docs' honesty about the Viewport row model — their own guidance is that people implement it when they should not. That kind of anti-recommendation builds more trust than a feature list.
What to avoid
  • The IoC container. It is why the core is large, why stack traces are unreadable, and why nobody contributes.
  • State inside the grid, reached imperatively. Every 'save this view' becomes bespoke serialise/restore, and role presets end up a second mechanism.
  • Per-developer perpetual licensing. It puts a procurement conversation before the first prototype.
  • A theming migration that breaks every consumer in a minor-looking major.
  • No domain semantics — every clinical meaning is a cellRenderer the customer writes and maintains.
TanStack Tablev9 stable · 4 Aug 2026MIT

The right shape for a design system to build on, and now the strongest engine numbers in the category — but it stops at the engine.

Core@tanstack/table-core is pure logic, framework-independent, exposing state as atoms and selectors.
StateTanStack Store on the alien-signals architecture, giving fine-grained reactivity; components subscribe to slices rather than to the whole table.
FeaturesExplicit registration via tableFeatures() — a table that only paginates client-side declares exactly that feature and that row model. Dead-code elimination that v8 could not do.
AdaptersTen adapters bind table atoms to native framework reactivity — Solid signals, Vue refs, Svelte runes, Angular signals — rather than working around React-shaped assumptions.
NumbersCore row processing +79%, grouping/aggregation +52%, sorting +37%, filtering +34%. Retained heap up to 86% lower: 380 MB versus 2.71 GB on a one-million-row, eight-column paginated case. Package 25 KB unminified, modular.
GapsNo virtualisation (separate library). No rendering. No accessibility. Server-side operations are a convention, not a contract.
What to take
  • Signals in the core. This is the most important single finding in this review: the best-measured engine in the category moved to signal-based reactivity and got 79% faster with 86% less memory. TC39 Signals is at Stage 1 with Angular, Vue, Solid, Preact, Ember and MobX contributors behind it.
  • Feature registration as the tree-shaking unit — the same idea as AG Grid's modules, expressed in a type-safe way.
  • Adapters that bind to native reactivity rather than forcing a React mental model on Angular.
  • The type inference. It is the best in the category and it is why developers who could use anything choose it.
What to avoid
  • Headless-only. Most consumers get accessibility wrong; shipping no keyboard model means the ecosystem is full of inaccessible tables built on an excellent engine.
  • Virtualisation in a different repository with a different mental model. The two hardest problems — row models and windowing — meet at scroll anchoring, and nobody owns that seam.
The number that matters: 380 MB retained heap for 1M rows × 8 columns, in the best engine in the category.
MUI X Data Gridv9 · 2026Community MIT · Pro US$299/dev/yr · Premium US$599/dev/yr

The best-designed declarative API and the best-designed server-data contract — inside a paywall that runs through table stakes.

APIDeclarative props, clean defaults, the most teachable of the commercial grids.
Data SourceGridDataSource with a single required getRows() returning GridGetRowsResponse, an optional updateRow(), and a real cache contract: set/get/clear, 5-minute default TTL, chunking to the smallest pageSize, per-request skipCache, background revalidation via dataSourceRevalidateMs, and typed GridGetRowsError / GridUpdateRowError.
Server featuresServer-side tree data, row grouping, lazy loading, aggregation and pivoting via extended data-source methods.
StylingTied to MUI's styling engine and theme.
TieringColumn pinning, tree data, row grouping and aggregation are paid. v9 adds an AI assistant and charts integration in Premium.
What to take
  • The Data Source contract. One required method, a typed error union, an explicit cache interface with a TTL, and documented invalidation — the best server-data design in the category, and better than what our brief specified.
  • The documented limitation that dataSourceKeepPreviousData applies only to flat data because tree and grouped data would show stale ordering. Publishing that kind of constraint is a mark of a serious library.
What to avoid
  • A free/paid boundary that runs through table stakes. A grid without column pinning is a demo, and a healthcare grid without pinned identity is unsafe.
  • A styling-engine dependency. It is the most-cited reason teams reject MUI X, and it is fatal for a component distributed as copy-source.
  • Row semantics that stop at getRowClassName — clinical meaning as a CSS class.
Handsontable2026Commercial; free only for non-commercial use. HyperFormula is GPLv3 or proprietary.

The best spreadsheet metaphor on the web, and the wrong metaphor for almost every clinical surface.

ModelSpreadsheet-first: a cell coordinate system, range selection, a fill handle, Excel-compatible paste.
FormulasHyperFormula — a headless TypeScript spreadsheet engine, 400+ functions, CRUD, undo/redo, clipboard, sorting.
FrameworksReact, Angular and Vue wrappers over one core.
LicensingThe important architectural fact. HyperFormula is GPLv3 unless you buy a proprietary licence; Handsontable itself is commercial for any commercial use.
What to take
  • Range selection, the fill handle and Excel-compatible paste are genuinely the right answer when the user's mental model really is a spreadsheet — charge capture and bulk coding.
  • A headless formula engine as a separate product is a good architectural pattern in itself.
What to avoid
  • GPLv3 by default. Vendoring or depending on HyperFormula would make our licence position radioactive for exactly the enterprise buyers we want. This is a legal landmine, not a preference.
  • The spreadsheet metaphor in clinical surfaces. It invites bulk paste into fields with clinical consequence.
  • Accessibility designed for a spreadsheet user, not a screen-reader user.
Syncfusion DataGrid2026Platform licence from roughly US$395/month, quote-based; community licence under US$1M revenue / ≤5 developers / ≤10 employees

The broadest feature surface and the one competitor already shipping AI in the grid — which retires one of our assumed differentiators.

FrameworksOne SDK across JavaScript, React, Angular, Vue, Blazor, ASP.NET Core and MVC — the widest framework reach in the category.
FeaturesExcel-like filtering, PDF/Excel export with formatting preserved, chart integration, virtualisation.
AIShips semantic filtering and anomaly detection in the grid today.
LicensingPlatform-wide, unlimited deployments, no runtime fees — but not transparently priced.
What to take
  • Platform licensing with unlimited deployment. For a healthcare vendor shipping to many provider sites, per-deployment fees are a deal-breaker and Syncfusion has removed that objection.
  • Export that preserves formatting. A stripped CSV is not what a biller wants.
What to avoid
  • Opaque pricing. It forces a sales call before evaluation, which is the opposite of the developer-led adoption we need.
  • Breadth over depth. 1,600+ controls means no single one gets the attention a data grid needs.
The number that matters: AI filtering and anomaly detection are already shipping in a competitor. Our AI section must be re-scoped around provenance, not features.
Glide Data GridcurrentMIT

Not on the brief's list, and the most architecturally interesting of all of them — because it proves the road we must not take.

RenderingHTML Canvas. No DOM nodes per cell. Visible cells are painted; scrolling repaints and discards.
MemoryFlat regardless of dataset size — 100 rows or 10 million cost the same.
HistoryIt began as DOM virtualisation with react-virtualized on both axes. The team moved to canvas specifically because loading and unloading hundreds of DOM nodes per frame was the bottleneck.
AccessibilityEvery cell is outside the accessibility tree by construction. What exists is a bolted-on overlay.
What to take
  • The diagnosis. Their stated reason for abandoning DOM virtualisation — per-frame node churn — is exactly why we must specify node recycling rather than assuming windowing is enough.
  • Damage-based repaint. Repainting only the changed region is the right model for a high-frequency clinical feed, and it maps onto DOM as targeted cell updates.
What to avoid
  • Canvas itself. For a surface a clinician uses for a full shift under WCAG 2.2 AA, taking every cell out of the accessibility tree is disqualifying. This rejection should be written down, because someone will propose canvas again the first time a scroll benchmark disappoints.

Missing capabilities discovered

Twelve things we had not considered

Twelve things the previous brief did not consider. Four are marked critical, meaning the design as written would have shipped a defect rather than merely missed a feature. Two of them invalidate claims the brief made prominently.

criticalFHIR pagination breaks the coverage sentence
What is true

FHIR servers return opaque link.next URLs and the specification is explicit that a client must not construct its own paging URLs. Bundle.total is optional; major servers return nothing or an estimate, and Azure's FHIR service supports only next — no first, last or previous.

Why it matters here

The brief's flagship sentence — “Showing 8 of 1,284” — is unavailable against a large share of real FHIR servers, and so is any page number or jump-to-page control. Coverage needs an honest unknown-total form and the pagination UI must degrade to next/previous only.

high`_include` breaks row-to-entry correspondence
What is true

FHIR applies _include and _revinclude after paging, so a page of 20 patients may return 140 entries.

Why it matters here

Any adapter that maps Bundle.entry.length to a row count is wrong. The adapter must partition by resource type and report what it could not map — the obligation ADR 0011 already places on adapters.

criticalCSV formula injection is an unhandled security defect
What is true

A cell beginning =, +, -, @, tab or CR is executed as a formula by Excel, Sheets and LibreOffice. OWASP notes that prefixing quotes is not sufficient — Excel can strip escaping on save-and-reopen, re-activating the payload — and that full-width variants (＝, ＋) execute in some locales.

Why it matters here

A patient's preferred name is free text a patient can supply. Export is therefore a remote-code-execution path from a patient into a biller's workstation. This is a defect in the design as written, not a missing feature.

criticalClient-side 1M rows was never achievable
What is true

TanStack Table v9 — the best-measured engine in the category — retains 380 MB for one million rows by eight columns, down from 2.71 GB in v8.

Why it matters here

The brief's performance table listed a 1M+ client-side row. On a 4 GB shared workstation running an EHR, 380 MB for eight columns is the entire budget, and a clinical grid has forty. The row should be removed and the refusal made explicit.

highSSR and hydration were not addressed at all
What is true

A virtualised grid renders 15 of 100,000 rows, so server and client markup differ and hydration fails. The common answer is to mark the grid client-only.

Why it matters here

Next.js App Router is the default stack for new digital-health products. “ssr: false and a shrug” is not an architecture — the answer is a server-rendered, non-virtualised first page that hands off to the client virtualiser, and it has to be designed rather than discovered.

criticalTelemetry and error reporting can leak PHI
What is true

An exception thrown inside a cell renderer conventionally carries the value that caused it. Error-tracking services store it.

Why it matters here

The grid must guarantee by construction that error objects and telemetry carry column keys and row indices, never values. No competitor addresses this and no healthcare buyer will fail to ask about it.

highNo renderer safety contract
What is true

Every competitor allows a custom cell renderer to return arbitrary markup. A cell rendering a note excerpt renders attacker-influenced content.

Why it matters here

The cell contract should make raw HTML injection impossible by type rather than discouraged in prose.

highMemory leaks are nobody's regression suite
What is true

Detached DOM nodes and un-removed listeners are the classic grid leak, and heap snapshots in CI with a growth threshold are a solved technique.

Why it matters here

A ward workstation keeps one browser session for a fortnight and mounts this grid hundreds of times a shift. No grid in this category gates on it, and the failure mode is a workstation that degrades over a shift — which gets blamed on the hospital's hardware.

highServer-side sort can be silently ignored
What is true

FHIR _sort support is server-dependent and several servers ignore an unsupported key rather than erroring.

Why it matters here

The grid would show an unsorted list under a header claiming a sort. It must detect the discrepancy and say so — a sort claim is a clinical claim once the column is a risk score.

mediumColumn spanning was used in our own mockup and never specified
What is true

The masking figure spans a Part 2 notice across three columns.

Why it matters here

Found by reading our own artefact. It is a reminder that the mockups encode requirements the prose did not capture.

@oxygenui-design/fhir is published; @oxygenui-design is the proven scope. The proposal's example names use @oxygenui/*.

Why it matters here

Five layers, and the two rules that hold them

Framework-agnostic strategy

Yes — and the condition under which I would abandon it

This is the question with the highest cost attached, so it deserves the most honest answer in the document. Yes — but not the way the diagram in your brief draws it, and not in wave one.

How the two credible models actually work

AG Grid is framework-agnostic by having no framework at all: a TypeScript core with its own IoC container, its own component abstraction and its own data binding, wrapped by thin per-framework packages. It works, it has for a decade, and the cost is a large unreadable core that nobody outside the company contributes to.

TanStack Table v9 is agnostic by being headless: a pure core exposing state as atoms and selectors, with ten adapters binding those atoms to each framework's native reactivity — Solid signals, Vue refs, Svelte runes, Angular signals. It is a better shape, and the cost is that it renders nothing, so every consumer owns accessibility and most get it wrong.

The variation this proposal makes

Neither model is right for us, for the same reason: the part we most need to write once is the part neither of them shares. AG Grid shares a renderer but hides it behind a framework nobody wants to learn. TanStack shares state but shares no rendering at all. Our differentiators — the ARIA contract, the keyboard model, the focus behaviour under virtualisation, the masking that survives copy and export — all live in the render layer.

So: a framework-free DOM renderer as a first-class package, below the adapters.

          grid-core          pure logic · signals · no DOM

An adapter's entire job is three things: own the mount point, marshal framework components into the renderer's cell interface, and bridge framework reactivity to core signals. If an adapter grows a fourth job, the strategy has failed and should be abandoned rather than nursed — which is a testable statement, because the cross-adapter accessibility-tree assertion will catch it.

The recommendation

  1. Build the core and renderer framework-free from the first commit. This costs almost nothing at the start and is close to impossible to retrofit.
  2. Ship React only in wave one. One adapter, fully supported.
  3. Do not claim agnosticism publicly until Angular exists. A README that lists four frameworks and supports one is the fastest way to lose the trust of exactly the engineering teams we want. Until a second adapter exists, the claim is untested.
  4. Angular second, not Vue. Behavioural-health and payer platforms skew Angular more than the React-first world assumes, and Angular's signals make it the adapter that best validates the reactivity choice.
  5. Vue, Svelte, Qwik and Solid are served by the custom element, not by four more packages. That is where a two-person team draws the line.

And the condition under which I would abandon this. If, at the end of wave four, the Angular adapter is larger than ~8 KB or contains any logic the React adapter also contains, the abstraction is in the wrong place. The correct response then is to stop at one framework and say so — not to keep paying a multiplier for a claim we cannot honour.

Package and repository structure

Why a separate repository is right, and what goes in it

Yes, a separate repository is correct — for three reasons, none of which is “it has become large”.

  1. Different release cadence and different consumers. OxygenUI ships components as copy-source that a customer owns and forks. A grid cannot work that way: it is a versioned dependency with a semver contract, a deprecation policy and a five-year support window. Those two distribution models do not belong in one repository.
  2. Different dependency direction. The grid depends on OxygenUI's L0 packages — tokens, FHIR types, intl. Nothing in OxygenUI should depend on the grid. Making that a repository boundary makes it enforceable rather than a convention.
  3. Different audience. A public repository with issues, benchmarks, a playground and a README written for an engineer evaluating AG Grid is a different artefact from a private design system.

And one reason it is risky: two repositories means a cross-repo dependency on @oxygenui-design/tokens that will drift, plus double the CI and governance overhead for a team that is currently one person and an agent. §26 prices that. The mitigating rule is narrow and should be written into the repository's own contributing guide: the grid may depend on OxygenUI L0 and nothing above it. If it needs an L2 component, that component moves down to L0 or is inlined.

Monorepo, not single package

A single package would force every consumer to ship the FHIR adapter, the AI plugin and the analytics WASM bundle. A workspace of small packages with subpath exports is the only shape that lets a patient directory stay at 26 KB while a claims ledger takes everything.

Core engine architecture

Actions for writes, signals for reads

The core is the part that must never change when a framework does. Everything in it satisfies three conditions: it has no DOM, no framework and no clinical vocabulary; it is testable without a renderer; and it can be serialised.

Two paths, deliberately different

Writes go through actions. A discriminated union reduced into state. This is what makes behaviour replayable, loggable and property-testable, and it is what lets the devtools panel show why a grid is in the state it is in.

Reads go through signals. Every derived value — the visible window, the group tree, the summary row, the chip set, the facet counts — is a computed signal, so a hover does not re-run filtering and a filter does not re-run grouping. This is where TanStack's +79% row processing and −86% heap came from, and it is not a micro-optimisation: it is the difference between a grid that is usable at 100,000 rows and one that is not.

// The write path: explicit, serialisable, replayable.
type GridAction =
  | { type: "sort/toggle"; key: string; additive: boolean }
  | { type: "filter/set"; node: FilterNode | null }
  | { type: "select/range"; from: RowId; to: RowId }
  | { type: "page/next"; cursor: string }
  | { type: "view/apply"; view: GridView };

// The read path: layered, memoised, pull-based.
const filtered   = computed(() => evaluate(source(), filter()));
const sorted     = computed(() => order(filtered(), sort()));
const grouped    = computed(() => group(sorted(), groupKeys()));
const disclosed  = computed(() => policy().apply(grouped()));   // before geometry
const window_    = computed(() => slice(disclosed(), viewport(), heights()));

Why the reactivity lives in its own package. grid-signals is a façade over an implementation — alien-signals today, native TC39 Signals when it ships. The core imports our interface, never a vendor's. TC39 Signals is Stage 1; if it lands, one package changes, and if it stalls, nothing does. That is the whole reason the indirection exists, and it is the only indirection in the core that is not load-bearing for a feature.

Row storage, and the one experiment worth running

The obvious representation is an array of row objects. It is also the wrong shape for a flowsheet: twenty analytes by two thousand timepoints allocates forty thousand objects for data that is natively columnar.

The recommendation is a storage interface in core with two implementations — row-oriented by default, columnar behind a flag — measured on the flowsheet fixture before either is made the default. Columnar storage is also the precondition for the Arrow/DuckDB path in §17, which is the only credible client-side answer above 100,000 rows. Nobody in this category does either.

What is deliberately not in core

  • Anything that touches the DOM, including measurement. The core computes geometry from heights it is told; grid-dom measures.
  • Data fetching. Core defines GridQuery and GridPage and nothing else. Whether that is TanStack Query, SWR or a SMART-on-FHIR client is the application's business.
  • Any clinical vocabulary. Core sorts comparables; it does not know what a reference range is.
  • An IoC container. Plain modules, explicit wiring. AG Grid's core is the cautionary tale.

What grid-dom owns

  • Node recycling. Not just windowing. Glide's team left DOM virtualisation because loading and unloading hundreds of nodes per frame was the bottleneck — so the rows entering and leaving the window are reused, with their content patched, rather than created and destroyed.

  • Focus that survives virtualisation. The focused cell's identity is { rowId, columnKey }, never a node reference — because the node it was on may have been recycled into a different row.
  • The cell renderer interface, which is what adapters marshal framework components into.

Plugin architecture

Six hooks, twelve slots, nothing arbitrary

You asked for grid.use(plugin) and warned against a plugin system that becomes impossible to maintain. That warning is the right instinct, and the way to honour it is to make the extension surface small, closed and typed — six hooks, twelve named slots, and no arbitrary render injection.

import { createGrid } from "@oxygenui-design/grid-core";
import { exportPlugin } from "@oxygenui-design/grid-export";
import { healthcare } from "@oxygenui-design/grid-healthcare";

const grid = createGrid({ columns, rowKey: "id" })
  .use(healthcare({ coverage, policy }))
  .use(exportPlugin({ formats: ["csv", "xlsx"] }));

// Types compose: `grid` now knows about `coverage`, `policy` and
// `grid.export()`. A plugin that is not registered is not in the type.

Four rules that keep it maintainable

  1. Slots are a closed set. Twelve named regions — toolbar, header menu, column menu, row affix, row detail, cell overlay, footer, empty state, error state, selection bar, coverage bar, live region. Not arbitrary render injection. Arbitrary injection is how a plugin system becomes an unversionable API surface where every internal DOM change is a breaking change for someone.
  2. Plugins pull, never push. A plugin contributes selectors and may veto actions. It may not write into grid state directly. This is what makes the state reconstructable from the action log.
  3. A veto carries a renderable reason. When the disclosure plugin blocks a copy, the grid must be able to tell the user why — so the veto is { blocked: true, reason: string }, never a silent false.
  4. Every plugin has a teardown() and the memory gate asserts it. A plugin that leaks fails CI rather than a customer's workstation.

What is deliberately not a plugin. Coverage, absence and the disclosure policy are in grid-healthcare as a package a consumer imports — but they are not optional behaviour once imported. A hideCoverage plugin would be the escape hatch ADR 0011 already rejected: a component that lets you switch off its safety claim does not have one.

2 · The cell host contract

Eight obligations now, not seven. The eighth is mask state, and adding it is what makes injection-safe, mask-preserving export possible at all — a cell that returns only a flat value cannot tell the export writer that the value must not leave.

3 · The recipes

Fourteen GridView documents plus column sets: roster, census, board, caseload, registry, work queue, flowsheet, MAR, chart list, plan, schedule, ledger, cohort, stream. Data, not code — which is what lets a product declare a caseload rather than build one, and lets a designer edit one.

4 · The enforced defaults

This is the part with no competitor equivalent and it is the actual product. In a clinical recipe:

  • the identity column is required: true and cannot be hidden;
  • clipboard and paste plugins are off by default;
  • a derived column without provenance does not compile;
  • aggregation across incompatible units refuses rather than coercing;
  • live updates are position-stable and arrivals queue;
  • and coverage is required with no escape hatch.

Why these are defaults rather than documentation. Every healthcare product makes these twelve decisions, in a hurry, differently, and they are exactly the decisions with clinical consequence. Documentation gets read once. A type error gets read every time.

Security and privacy architecture

Three defects, and the boundary

The previous brief had a good disclosure model and no software security model at all. Those are different things, and a healthcare buyer's security review will ask about the second.

Three defects to fix before the first release

  1. Export is a code-execution path. Formula injection, covered in §06. The defence belongs inside the writer with no way to switch it off, XLSX with typed cells is preferred for anything a human opens, and there must be a test with the payload in a patient-name fixture asserting the emitted bytes.
  2. Telemetry can carry PHI. An exception thrown inside a cell renderer conventionally carries the value that caused it, and error-tracking services store it. Guarantee it by construction: error objects and telemetry carry { columnKey, rowIndex, code } and never a value. A lint rule and a test that throws inside a renderer and asserts the reported payload contains no fixture string.
  3. Custom renderers can inject raw HTML. Every competitor allows it. Our cell contract should make it a type error: a renderer returns text, a token, or a component — never a markup string. A cell rendering a note excerpt is rendering attacker-influenced content.

Performance architecture

Accessibility strategy

Written once, below the adapters

The brief's accessibility work was its strongest section and it survives intact. Three additions, all of which follow from the architecture change rather than from a gap in the analysis.

  1. It lives in grid-dom, once. This is the strongest argument for the whole framework-agnostic strategy: the keyboard model, the ARIA contract and focus-under-virtualisation are written a single time and are identical in React, Angular, Vue and vanilla. Every multi-framework component library that puts accessibility in the adapters ends up with four subtly different implementations, and the fourth one is always the worst.
  2. Cross-adapter parity is a test, not a promise. One assertion over the rendered accessibility tree, run against every adapter, from the day the second adapter exists. OxygenUI already does exactly this in e2e/bridge-hosts.spec.ts, which renders one application under antd, MUI and neither and asserts the trees are identical.
  3. A remappable keymap. The keymap is data in grid-core, so it can be replaced. A clinician with nine years of muscle memory in one EHR has something worth more than our defaults, and no competitor does this well. It is a genuine differentiator for the one user who spends a whole shift in the grid.

The parts that carry over unchanged

  • The body is one tab stop with a roving tabindex inside it. A tab stop per cell is 800 presses to leave a 40×20 grid.
  • Absolute aria-rowindex under virtualisation — the defect that makes so many grids announce “row 1 of 20” forever. With the FHIR finding, aria-rowcount="-1" also becomes a real case rather than a theoretical one: it is the correct value when the server genuinely does not report a total.
  • Every operation reachable by keyboard, asserted by tests that never dispatch a pointer event — the construction that makes the Signature component's Level A claim a test rather than a sentence. WCAG 2.2 SC 2.5.7 makes drag-only column reorder a failure, and no competitor has a complete keyboard path for resize, reorder, hide and pin.
  • Focus not obscured (SC 2.4.11) — the grid-specific trap, where a sticky header covers the focused cell when you arrow upward.
  • Forced colors, reduced motion, 200% zoom, 320 px reflow, RTL via logical properties — all already gated in OxygenUI CI across three engines.
  • The screen-reader matrix is the release gate, published with its gaps. NVDA, JAWS and VoiceOver × Chromium, Firefox and WebKit, against the 40,000-row virtualised fixture. It cannot be automated and should be planned as work rather than discovered as a blocker.

One thing to add that the brief did not mention: voice control. Dragon and Voice Control drive by accessible name, so every interactive element in the grid needs a name a person would actually say — “sort by risk”, not “button”. It costs nothing if the names are right from the start and is a retrofit if they are not. Clinical settings have a higher-than-average density of voice-control users.

AI extension strategy

The features are table stakes; the refusal is not

The brief treated AI as a differentiator. That is no longer true and the section needs re-scoping around what is.

Syncfusion ships semantic filtering and anomaly detection in its data grid today. MUI X v9 ships an AI assistant in Premium. Natural-language filtering is table stakes, not an edge. Anything we build here will be matched within two releases.

What is actually defensible

Provenance, refusal and confirmation. Every competitor's AI feature produces an answer. Ours should be the only one that can produce no answer, visibly, and the only one where an AI-derived value cannot be mistaken for a verified one at a glance. That is not a model capability — it is a type system and a rendering contract, and it is very hard to retrofit into a product that shipped without it.

  1. AI output is a provenance state of a value, not a kind of column. The catalogue already has the states: ClinicalStatus has AI draft, ResultValue has AI extracted, ProvenanceChip has the whole chain. Nothing new is needed to render AI honestly, and anything that invents a new treatment is creating a second vocabulary for the same idea.
  2. Never mix generated and verified values in one cell. A row may mix; a cell may not, because a reader reads a cell as one fact.
  3. Distinguishable without colour. A glyph and a word. A purple tint disappears in forced-colors mode, which is precisely where it must not.
  4. The proposal channel never writes. AI may propose a filter, a column, a grouping or an action. Applying it is a human act, and the applied artefact is always the same kind of object a human could have made by hand — which is what makes it reviewable and reversible.
  5. An uncompilable query runs nothing. No approximation, ever. A silently narrowed cohort looks exactly like a correct answer, and in a clinical list that is the most dangerous single failure available.

PHI and the model boundary

  • Natural-language filtering needs the schema, not the data. Column keys, types and enum values compile a query. No row ever leaves the browser for a filter. This is both a privacy property and an architectural one, and it should be stated in the plugin's own documentation.
  • Row summarisation does need the row, so it is a different risk class and a different consent conversation. It must be separately switchable, and the application must supply the endpoint — we never choose a provider on a customer's behalf.
  • Anomaly detection runs locally where it can: an outlier against the visible cohort is arithmetic, not inference, and calling it AI when it is a z-score would be dishonest labelling.

Hallucination, concretely

The risk is not a wrong sentence in a summary. It is a plausible filter. “High-risk patients who missed appointments this month” has at least four ambiguities — which risk model, which threshold, what counts as missed, whose month — and a system that resolves them silently produces a defensible-looking cohort that is wrong in a way nobody can see. Hence: compile to chips, show the chips, and require the human to press run. The previous brief got this right and it remains the strongest AI idea in either document.

And the structural rule. grid-ai is a plugin in its own package with its own dependency on copilot-core. Core has no AI code, no AI types and no AI-shaped extension points. A clinical list must be able to exist with no model anywhere near it.

Risks and technical debt

Ten risks, and the one that is not on the list

Ten risks. Two are marked critical, and only one of those is technical.

criticalFramework agnosticism multiplies the maintenance surface
The risk

Four adapters means four release matrices, four test suites, four documentation sets and four bug queues — for a team that is currently one person plus an agent.

Mitigation

Mitigate by putting the DOM renderer below the adapters. If adapters are 4 KB of binding and contain no grid logic, the multiplier applies to a small surface. If any adapter grows a feature, the strategy has failed and should be abandoned rather than nursed. Ship React only in wave 1; do not claim agnosticism until Angular exists.

highA separate repository doubles the release and governance overhead
The risk

Two repos, two CI configurations, two changelogs, and a cross-repo dependency on @oxygenui-design/tokens that will drift.

Mitigation

Accept it, but only with a rule: the grid may depend on OxygenUI L0 packages and nothing else. If it needs an L2 component, that component moves down to L0 or is inlined.

highThe grid becomes a second design system by accident
The risk

A grid that owns its own theming, its own icons and its own intl is a competing system with the library it came from.

Mitigation

Forbid it structurally: grid-dom may reference tokens and may not define them. A contrast gate runs against the OxygenUI token surface, not a local one.

highScroll anchoring across dynamic row heights
The risk

The single hardest engineering problem here, and the one most likely to be subtly wrong for months. Glide abandoned DOM virtualisation over exactly this.

Mitigation

Budget it explicitly in wave 2 with its own acceptance test, and specify node recycling from the start rather than discovering the need.

The five sentences that define this architecture

  1. The engine has no DOM, no framework and no clinical vocabulary, so it is testable without a renderer and reusable outside healthcare.
  2. The renderer sits below the adapters, so accessibility and virtualisation are written once.

  5. Everything optional is a package, and a package that is not imported costs zero bytes.

The verdict

Build it. Separate repository, framework-agnostic core, React first.

The clinical thesis is genuinely differentiated and the category is genuinely open — Terra UI, Cerner's React design system and the only serious healthcare component library, was archived on 28 June 2024 along with the entire Cerner GitHub organisation, and nothing has replaced it. There is no healthcare-native grid to compete with. That is unusual and it will not last indefinitely.

But the previous design would not have produced a library another engineering team evaluates. It would have produced a very good React table for one product, with a security defect in its export, a physically impossible performance claim, and a flagship sentence that FHIR cannot support. All three are free to fix today.

Six conditions I would attach

  1. Do not claim framework agnosticism until the second adapter exists. A README listing four frameworks and supporting one loses precisely the audience it is aimed at.
  2. Fix the three security defects before the first export ships. Injection-safe writer, PHI-free telemetry, renderer safety by type. None is expensive now; all are structural later.
  3. Delete the 1M client-side claim and replace it with a refusal. Refusing loudly, with a number and a reason, builds more credibility than a benchmark table.
  4. Decide the licence and support posture before the repository is public. My recommendation is MIT for everything a security reviewer must read, commercial only for an enterprise recipe pack.
  5. Name a clinician reviewer and budget for them before wave three. This is the fourth artefact blocked on it. Until then every clinical rule here is a well-researched proposal, and should be labelled as one.
  6. Keep wave one shippable alone. Six waves is a lot of runway for one person and an agent, and the architecture must make stopping a decision rather than a failure.

And the one thing I would push back on hardest

The target you set — a grid that healthcare enterprise teams evaluate before AG Grid — is achievable, but not by matching AG Grid. It has a decade in its virtualiser and the only mature server-side row model in the category, and we will not out-build that with the resources available. The way to win the evaluation is to be the only grid where a clinical safety officer can sign off in an afternoon — because the absence taxonomy, the coverage declaration, the disclosure policy and the sort provenance are in the types and gated by tests rather than left to whoever is on the ticket. That is a different axis, it is one AG Grid has no reason to compete on, and it is worth more to the buyer than pivot mode.

If only one thing from this review survives, make it the framework-free DOM renderer sitting below the adapters. Everything else in this document can be changed in a later release. That one cannot.
